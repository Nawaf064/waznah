# إدارة كتالوج وزنة

نُشرت قواعد Firestore بنجاح يوم 17 أكتوبر 2026، ونُشر الكتالوج بالإصدار 1 يوم 22 أكتوبر 2026 على مشروع waznah-47376: 13 قطعة، ورشتان و6 خدمات. أُعيدت قراءة نسخة الخادم وتحققت مطابقتها. أُلغي دخول Google المؤقت بعد النشر؛ أداة Admin SDK تحتاج Application Default Credentials مستقلة عن دخول Firebase CLI عند التحديث التالي. لا تضف مفاتيح خدمة إلى التطبيق أو المستودع.

## الهيكل

المستند `catalog/published` يحتوي نسخة ذرية واحدة: `parts` لهوية القطع والتوافق، `offers` لعروض البائعين مرتبطة بـ `partId`، `workshops` للمواقع، و`services` لأجرة العمل. الأموال أعداد صحيحة بالهللة. أنواع سعر الخدمة: طلب تسعير، بداية سعر، أو نطاق أسعار بداية. كل سعر له مصدر وشروط؛ تاريخ `reviewedAt` للدفعة، والتفاصيل الأقدم تبقى في ملاحظاتها. الحد المحلي 750KB، ثم يلزم تقسيم الإصدارات إذا كبر الكتالوج.

القراءة للمستخدم المسجل فقط. الضيف يستخدم البيانات المرفقة بالتطبيق. لا يوجد سماح كتابة من تطبيق الجوال لأي مستخدم، حتى لو أضاف حقل admin لحسابه. النشر عبر Admin SDK وصلاحيات IAM للمسؤول فقط. إعداد IAM يتم خارج التطبيق.

## تجهيز أول نسخة

1. `dart run tool/catalog.dart export data/catalog-draft.json`
2. عدّل المسودة؛ احتفظ بمعرف القطعة عند تعديل السعر، ولا تخلط ثمن الطقم والحبة. لا تضع حدود نطاق بلا مصدر.
3. `dart run tool/catalog.dart validate data/catalog-draft.json`
4. راجع واختبر `firestore.rules` في محاكي Firebase قبل نشرها. تشمل القطع الـ13 ومعرفات الكتالوج المنشور وفحص كميات 1–99 وحدود 200 عنصر.
5. ثبت اعتماد أداة الإدارة: `npm install --prefix tool/admin`.
6. جهز Application Default Credentials لحساب مسؤول مخوّل للمشروع، خارج ملفات التطبيق. استخدم متغير WAZNAH_DART لمسار dart.exe إن لم يكن على PATH.
7. بعد نشر القواعد والتحقق منها: `node tool/admin/publish.mjs data/catalog-draft.json --publish`.

في التحديث التالي ابدأ من النسخة المنشورة وزد revision بواحد. الأداة ترفض تعارض النسخ بدل الكتابة فوق تحديث مسؤول آخر. للرجوع انشر المحتوى السابق برقم إصدار جديد. لا تحذف معرفات قطع مستخدمة في قوائم العملاء؛ اترك القطعة دون عروض متاحة إن توقفت.

## تحديث نسخة منشورة

بعد تجهيز دخول مسؤول مؤقت، نزّل النسخة الحالية إلى ملف جديد:

```text
node tool/admin/download.mjs data/current-catalog.json
dart run tool/catalog.dart prepare data/current-catalog.json data/next-catalog.json
```

التنزيل يقرأ الخادم فقط، ويفحص البيانات قبل إنشاء الملف. التجهيز يعمل محليًا دون دخول Google، ويحافظ على المحتوى ويزيد رقم الإصدار. كلا الأمرين يرفضان استبدال ملف موجود. عدّل الأسعار وملاحظات المصادر في الملف الجديد ثم افحصه وانشره:

```text
dart run tool/catalog.dart validate data/next-catalog.json
node tool/admin/publish.mjs data/next-catalog.json --publish
```

إذا تغير إصدار الخادم أثناء عملك سيرفض النشر؛ نزّل نسخة حديثة وراجع تعديلاتك عليها. لا تغيّر رقم الإصدار فقط لتجاوز التعارض. بعد النشر والتحقق، ألغِ الدخول المؤقت باستخدام `gcloud auth application-default revoke --quiet`.

## استعادة محتوى إصدار سابق

مثال استعادة محتوى الإصدار 1 بعد أن أصبح ضمن السجل:

```text
node tool/admin/download.mjs data/current-for-restore.json
node tool/admin/download.mjs data/history-1.json 1
dart run tool/catalog.dart prepare data/current-for-restore.json data/restore-draft.json data/history-1.json
dart run tool/catalog.dart validate data/restore-draft.json
```

راجع المسودة ثم انشرها بأمر النشر المعتاد. تُستعاد الأسعار والمحتويات برقم إصدار جديد؛ لا يُرجع رقم الإصدار للخلف. إذا كانت النسخة القديمة تفتقد قطعًا أُضيفت لاحقًا، يرفض التجهيز؛ يلزم إبقاء تلك القطع ومراجعة عروضها حتى لا تتعطل المفضلة وقوائم الصيانة. لا يوجد سجل للإصدار الأول حتى يُنشر الإصدار التالي ويحفظه تلقائيًا.

اختبارات الإدارة المحلية: `node --test tool/admin/catalog-cli.test.mjs tool/admin/publication.test.mjs`. اضبط `WAZNAH_DART` على مسار Dart إذا لم يكن موجودًا على PATH. التنزيل من الخادم يحتاج اختبار اتصال وصلاحية عند الاستخدام؛ نجاح الاختبارات المحلية وحده لا يثبت ذلك.

عند تحديث كتالوج منشور تحفظ الأداة المحتوى السابق في `catalog_history/revision-N` ضمن المعاملة نفسها. فشل إنشاء النسخة السابقة يمنع تحديث النسخة النشطة. يمنع النشر حذف أي معرف قطعة منشور سابقًا. سجل النسخ مغلق أمام تطبيق العملاء. للتحقق المحلي من هذه السياسة: `node --test tool/admin/publication.test.mjs`؛ هذه الاختبارات تحاكي المعاملة ولا تتحقق من اتصال أو صلاحيات Firebase.

ملف firebase.json مخصص لقواعد Firestore ومحاكيها المحلي فقط؛ أزيل إعداد نشر المتصفح بعد إلغائه. ثُبت Firebase CLI وأدوات اختبار القواعد، ونجحت اختبارات `firestore-rules.test.mjs` الإحدى عشرة على محاكي Firestore بمشروع `demo-waznah-rules`. لتشغيلها بعد تجهيز Java: `node tool/admin/node_modules/firebase-tools/lib/bin/firebase.js emulators:exec --project demo-waznah-rules --only firestore "node --test tool/admin/firestore-rules.test.mjs"`. لا تستخدم بيانات مشروع الإنتاج لاختبارات الأمان.

## اختبار الحسابات محليًا

أضيف محاكي Authentication على `127.0.0.1:9099` بجانب Firestore على `127.0.0.1:8080`. هذه الإعدادات تخص أدوات التطوير فقط؛ تطبيق الجوال لم يُحوّل إلى المحاكي. بعد تجهيز Java:

```text
node tool/admin/node_modules/firebase-tools/lib/bin/firebase.js emulators:exec --project demo-waznah-rules --only auth,firestore "node --test tool/admin/auth-flow.test.mjs"
```

نجحت أربع تجارب فعلية على المحاكيات: إنشاء الحساب وإعادة الدخول مع استرجاع المفضلة، تأكيد البريد ورفض إعادة استخدام الرمز، إعادة تعيين كلمة المرور مع بقاء هوية الحساب والبيانات، وعزل حساب ثانٍ عن بيانات الأول. الاختبار يرفض العمل ما لم يكن المحاكيان على العنوانين المحليين المحددين ويستخدم مشروع `demo-` فقط. البريد `example.test` والرموز محلية؛ لا تُرسل رسائل بريد حقيقية ولا تُنشأ حسابات في الإنتاج. نجاحه لا يثبت وصول رسائل البريد الفعلية أو تجربة واجهة أندرويد كاملة.

## حدود التحقق الحالية

اختبارات Dart تغطي فساد البيانات، مصادر الأسعار، نطاقات الأجرة، تغير الأسعار في مجموع الصيانة، وفشل القراءة والرجوع لآخر نسخة. اختبارات قواعد الخادم والنشر الفعلي والتحقق بحساب حقيقي لا تعتبر منجزة بمجرد نجاح اختبارات Dart. أداة الإدارة تجهيز تقني؛ لم تُنجز واجهة إدارة رسومية.
